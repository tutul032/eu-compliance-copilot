# 3. Identity and ownership: dedicated CI/CD service principal, additive grants only

- **Status:** Proposed
- **Date:** 2026-11-03

## Context
ADR 0001 left this project with no service principals or grants: the platform owner's user owns
all three `compliance_*` schemas. Staging and prod must be deployed by an automated identity, not
by a person's account.

The Free Edition workspace and its `workspace` catalog are shared with Project 1
(energy-lakehouse-de), which manages its own service principals and grants on that catalog from a
separate Terraform state. Neither state knows about the other's grants.

## Decision
- **One service principal per project.** `sp-eucc-cicd` is new and created by Terraform (no
  import). It does not reuse `sp-energy-cicd`, so each project's access can be reviewed and
  revoked, and its secret rotated, without affecting the other. Its entitlements match Project 1's
  CI/CD SP: workspace and SQL access, no cluster or instance pool creation.
- **The SP owns staging and prod.** `compliance_staging` and `compliance_prod` are owned by the
  SP's application ID, so that it holds full rights on the targets it deploys without per-privilege
  grants. `compliance_dev` stays owned by the platform owner's user.
- **Only non-authoritative grants on shared securables.** Grants use `databricks_grant`
  (singular), which is authoritative only for one principal on one securable. Never
  `databricks_grants` (plural), which is authoritative for every principal on a securable: on the
  shared catalog, an apply from this state would revoke Project 1's grants and the
  `_workspace_users` grant. The grants are `USE_CATALOG` on the catalog for the SP, and `SELECT`
  and `USE_SCHEMA` on staging and prod for the platform owner, who loses access there when
  ownership moves to the SP.
- **The secret is created manually and stored only in GitHub secrets.** It is generated by hand in
  the workspace and pasted into GitHub. There is no `databricks_service_principal_secret` resource,
  because Terraform would write the value to its state in plain text.

## Consequences
- Removing a grant from this project cannot affect Project 1, and the reverse. The price is that
  neither state detects grants added outside it: drift on other principals stays invisible.
- The platform owner no longer owns staging and prod. Changes there go through the SP, and direct
  access is limited to reading.
- Creating and rotating the secret is a manual step that Terraform cannot detect or enforce. A
  fresh environment needs it done by hand before CI can authenticate.
- Nothing in the code enforces the singular-only rule yet; it holds through review until a check
  is added.
- The SP is not wired into the bundle or CI yet: `databricks.yml` sets no `run_as` and `ci.yml`
  uses no Databricks secrets.
